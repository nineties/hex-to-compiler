planck0

planck0 reads only M-expressions. It compiles each top-level M-expression to bytecode as it reads it, and runs the bytecode on a virtual machine that keeps its frames on the heap. The source is the single file planck0.sv.

Top level

main prepares the state, reads planck/init.pk, and then reads the program file given as the first argument.

interpret_file reads a file ([[planck0.sv#2566-2595]]). For each expression it calls the global variables parse and eval again through call_global. call_global builds Apply{name, Tuple{arg}}, compiles it and runs it ([[planck0.sv#2561-2564]]). Therefore a program that replaces parse has the next expression read by the new parse. The syntax of planck enters by this mechanism.

Value representation

A value is one 32-bit word. When the least significant bit is 1, the value is an integer shifted left by one bit. When it is 0, the value is a pointer to an object on the heap. An object has a header word that holds its kind and length.

Symbols and M-expressions are interned. M-expressions with the same structure are one object in memory, so equality is pointer comparison ([[planck0.sv#329-338]]).

The heap is a 1 GB region allocated by mmap2 at startup and carved from the front. There is no GC ([[planck0.sv#36-67]]).

The M-expression reader

The builtin parse reads four kinds of text: symbols, integers, strings, and Head{...}, where a { follows a symbol directly ([[planck0.sv#784-874]]). An M-expression has at most 16 arguments.

After the syntax of planck is installed, this reader remains as parse_mexpr.

The compiler

compile turns an integer or a string into a constant and a symbol into a variable reference, and passes an M-expression to compile_mexpr ([[planck0.sv#1445-1460]]).

compile_mexpr dispatches on the head ([[planck0.sv#1270-1443]]). The special forms are Apply, Def, Set, Do, If, While, Lambda, Fusion, Quote, QuasiQuote, Handle and Perform. Any other head is a constructor: it evaluates the arguments and builds an M-expression with the same head.

The compiler resolves a local variable to a pair (environment depth, position) at compile time. A top-level Def and an unbound name are global variables, which are looked up in a table at run time. This is why a top-level function can refer to itself.

The virtual machine

The machine has 18 instructions. The design is described in the comments of the source.

Frames live on the heap, not on the machine stack, and the virtual machine does not call itself recursively. The state of a computation is the chain of frames from the current frame to the top level, so a continuation is a pointer to this chain.

Calls and pattern matching

At a call, select chooses the function that matches the arguments ([[planck0.sv#1616-1644]]). A Fusion tries the left function and, on failure, the right one. A Lambda compares the number of arguments and then matches the patterns in order.

match_pat writes the value to the next position of the new environment for a variable, compares equality for a Quote, and checks the kind for a _TypeOf before it matches the inner pattern. An M-expression pattern compares the head and the number of arguments, and recurses on each argument. When no function matches, the program stops with matching failed ([[planck0.sv#1698-1710]]).

The builtin eval compiles an M-expression as a top-level expression and runs it in a new frame ([[planck0.sv#1675-1679]]).

Builtin functions

init_prims registers the builtin functions in the global table with defprim. defprim takes the name, the number of arguments, the implementing function and the kind ([[planck0.sv#2459-2467]]). The operators and the string concatenation are registered under the names that the sugar calls. These names start with _: _add, _sub, _mul, _div, _mod, _lt, _le, _gt, _ge, _eq, _ne and _strcat ([[planck0.sv#2469-2524]]). Names without _, such as add and strcat, are not registered. A variable of the same name in a program does not change the meaning of an operator.

Effects

Handle runs its body in a new frame and records the handler in that frame ([[planck0.sv#1825-1832]]). Perform follows the chain from the current frame to the callers and looks for a frame that has a handler.

When it finds one, it makes a continuation k, a pair of the current frame and the boundary frame, and matches the handler against (v, k). When the handler does not match, the search continues outward. The value of the handler returns to the caller of the boundary frame and becomes the value of the Handle expression.

Calling k copies the frames from the current frame to the boundary and runs the copy (resume, [[planck0.sv#1646-1663]]). The original frames never run, so the same k can be called any number of times (multi-shot continuations).
