planckvm instructions

This page is part of the external specification of planckvm: the instructions, the builtin functions, and how each feature of planck is translated into instructions. The machine and the values are in planckvm: execution model and values. The design inside an implementation is in planckvm internals.

Notation: the stack is written with the bottom at the left, and a b -> r pops two values and pushes one. Operands: k an index of the constant table, c a cell (a k), d i a depth and an index of the environment, L an index of the instructions, n a count, p the value of a builtin instruction. Mark columns: S a safe point where an allocation may run the collector, W a write that is recorded, T the program stops unless the condition holds.

A program can assign a global function such as _index_get, so a + b cannot be fixed to ADD. CALLP keeps such an override working.

The entry of a function has one instruction sequence for each pattern. When a match fails, the program goes to L and empties the operand stack. At L there is a NEXT. When an argument is bound to a variable of the pattern, STORE 0 i and POP write it into the environment. There is no instruction that fuses PARAM, STORE and POP.

A call in the tail position of the body of a HANDLE is written TCALL, but the boundary frame is not dropped.

ADD, SUB, MUL, DIV and LT stop on an argument that is not a number. The mixing of types and the result type are in Numbers of the execution model. The instructions from HEAD to PLAINSET stop on an argument of a wrong type or out of range (except ORD out of range).

Builtins and instructions

Only what is called at a high frequency is an instruction: the constants, variables, control, calls, matching, effects and operators that every run goes through, and the builtins that are called the most. Everything else is a builtin function, and no instruction is added for it. An operation that differs by type is one instruction that looks at the type of its value.

Builtins that are not instructions

Those of the kind planck are planck functions that use the instructions, and are part of the image of the evaluator. The names of the global variables and the behavior are the same as those of the builtins. Those of the kind machine are builtins of the machine (the Builtin of the table in Calls of the execution model). Both are called with GLOAD c, the arguments and CALL n.

The allocations and errors of a machine builtin are covered by the S and T of the CALL that called it. mexpr, substr, _strcat, intern, symname, array, plain_array, plain_len and plain_kind are also errors for an argument of a wrong type or out of range.

The arguments of the bit operations are integers, treated as infinite-width two's complement, negative numbers included.

A builtin that takes a float also takes an integer and raises it to a float. A complex number is an error. The mathematical functions are exactly these six: fexp flog fsin fcos fpow fatan2. The addition, subtraction, multiplication, division and equality of complex numbers are written with ADD, SUB, MUL, DIV and EQ.

eval is the only builtin that makes a frame. If a PERFORM happens during it, the frames inside the eval are ordinary frames and can be copied.

The name of a function in an error message can differ from the builtin that was called. For example the message for a non-integer argument of _mod names _div.

Names defined by planck code

The names in the table of builtin functions of the specification that are not builtins of the machine are defined by planck code and need no instruction: _define_rule _index_get _index_set _not _record_declare _record_get _to_text false load none parse_mexpr peg_for peg_parse subst table table_get table_set true use used_libs.

The new builtins that planckvm adds to the specification are plain_array, the float functions fsqrt ffloor ftoi ftobits bitstof ftos stof fexp flog fsin fcos fpow fatan2, the complex functions complex real imag, the array makers of each plain type, itof and conj.

Where the rules depend on the place

An instruction does not change its meaning with the place. The difference is in the instruction that the compiler picks.

PlaceRuleEffect on the instructions
x := e at the top level, outside a blockA global variable. A new cell is madeGSET c
x := e in the block of an if or while at the top levelA local variable in the environment of the top-level codeSTORE 0 i
x := e in a functionA local variable: a new slot of the same functionSTORE 0 i
Declare{x} (the first half of f(p) := e)Nothing if a variable is at the same place. At the top level, the same place means a global variable defined by the file being loaded; a global variable of another file is made anew and hides itA decision at compile time with the file given by _set_file
Declare{x} in a functionOnly a variable of the environment of the same function is at the same place. A variable of an outer function is notA decision at compile time
A tail callTCALL in every place. The result is the same and only the depth of the stack differsThe choice of instruction does not depend on the place
A tail call in the body of a HANDLEWritten TCALL, but the boundary frame is not droppedA rule at run time
A name that is not foundStops at compile time before the expression runs, in every placeNo instruction is produced
A forward referenceDeclare with fun f first, in a function and at the top level alikefun f starts as none and stops when called (not a function: none). GLOAD and LOAD do not check
